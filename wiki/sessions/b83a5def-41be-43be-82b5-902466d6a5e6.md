## Part 2: the real bug — two problems stacked

The friend's debug files (dropped into a local `.bugs/` folder for this session) revealed her CE-project wiki search was returning nothing useful, even though the wiki was populated (her run log showed 5 pages applied from 10 sessions). Investigation found two independent, stacked causes:

1. **Unregistered project + no `@` selector → silent fallback.** She has used memoria since before the `update` command existed, so her install was a manual clone of the memoria repo itself — and that clone's own folder was never registered with `memoria bootstrap`. Every MCP call resolves the calling directory to a tracked project first; a plain query with no `@` selector requires that resolution to succeed, and hers didn't — it hit `not inside a tracked project (run memoria bootstrap first)` before the query even ran. Her Claude Code session then silently fell back to its own built-in conversation/transcript search (visible in her transcript as \"Queried session store\" — not memoria at all), found one local session, and reported the CE wiki as having nothing more — full findings in [[gotchas/unregistered-project-search-silent-fallback]].
2. **`searchWiki` was pure substring match.** Even once registered, multi-word phrase queries would still fail: her own debug showed `decay` returning 7 pages but `decay session pages` returning 0, despite [[concepts/session-decay]] and related pages existing and matching each individual term. Full findings and the fix in [[gotchas/search-substring-only-false-negatives]].
