# Session: processor E2BIG root cause + process --inspect

**2026-07-28 16:26–16:42 · project memoria · commit `a04b554`**

## Part 1: why processing the bc1657* session failed

The user hit an on-screen error trying to `memoria process` the session digest whose name starts with `bc1657`. Diagnosis from `~/.config/memoria/memoria.log`: the 16:25:40 run picked up 2 sessions, then died with `claude: fork/exec: argument list too long`.

Root cause at `processor.go:45`: the whole consolidation prompt was passed as a single argv element. Linux caps one argv element at 128 KiB (`MAX_ARG_STRLEN`); the prompt bundled the wiki prompt + the full 20-page wiki + the session digests, including the 119 KB `bc1657b9...` digest — over the limit, so `execve` failed with E2BIG before claude even started.

Fix: the prompt now goes via stdin (`cmd.Stdin = strings.NewReader(prompt)`). `claude -p` reads stdin natively; the codex invocation changed to `codex exec -` (`-` = read stdin). Stdin has no size ceiling. Regression tests added in `processor_test.go`:

- `TestRunProcessorCmdLargePromptViaStdin` — 300 KB prompt through `cat`, the exact scenario (the old code was verified to fail E2BIG at the same argv size)
- `TestRunProcessorCmdPromptNotInArgv` — prompt absent from argv even when small, so the regression can't sneak back
- `TestRunProcessorCmdReportsStderr` — error path keeps stderr detail

Durable lesson recorded in [[gotchas/prompt-over-stdin-argv-limit]].

## Part 2: memoria process --inspect

The user asked for a way to connect to a running background job. Implementation:

- The detached child's stdout/stderr now land in `~/.config/memoria/<project>.run.log` (truncated each run) instead of being thrown away — `spawnDetached` wires the file, so lint and seed background runs write there too.
- `--inspect` tails that log while the recorded pid is alive (500 ms poll), then prints final status from `status.yaml`. Ctrl-C detaches without touching the job; nothing running → points at `memoria status`.
- The child prints "Invoking claude-code with N session(s)..." before the LLM call, so inspect shows something immediately. Progress during the LLM call itself stays coarse — the claude CLI is silent in `-p` mode.

Skipped: socket/IPC attach — log file + pid poll covers it.
