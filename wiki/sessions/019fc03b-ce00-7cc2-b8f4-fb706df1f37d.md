## Work

Started with a directive: evaluate Memoria objectively — what's good, what's broken, what can improve. ## Durable findings

Memoria's core design is sound: plain Markdown source-of-truth, human review gate, constrained LLM role. Flaws cluster around concurrency, identity, staleness, and privacy:

- **Concurrency**: three patches (flock on queue files, digest-size growth detection, job-claiming status checks) work around missing atomic leased state. ai-memory uses a persistent server + SQLite transactions for total ordering.
- **Identity**: basename-keyed projects collide in monorepo/multirepo scenarios. ai-memory uses workspace/project UUIDs at the storage layer (display names separate).
- **Staleness**: proposals lack source-page hash, enabling overwrites of human edits. ai-memory snapshots target ID, body hash, and `updated_at` inside proposals; apply-time conflict detection refuses stale writes.
- **Privacy**: full user prompts, Bash commands, and errors are captured unredacted and sent to remote processors. ai-memory adds typed sanitization boundaries, credential pattern redaction, per-file exclusions, and double opt-in for assistant-text capture.
- **Lint coverage**: 400-character previews of ≤20 pages miss contradictions deeper in the text. ai-memory's deterministic lint (link checks, title deduplication, field validation) is stronger, though semantic contradiction pass remains shallow.

Key transferable improvements (no server/database required): stable project UUIDs (not basenames), proposal target snapshots (enable conflict detection), atomic job leases (one-writer actor or transactional state), privacy redaction (before persistence), bounded context selection (tags + wikilinks instead of entire wiki), structured output validation (tag syntax, duplicate paths, page count), and audit trails (page hashes, source session IDs, generation time).
