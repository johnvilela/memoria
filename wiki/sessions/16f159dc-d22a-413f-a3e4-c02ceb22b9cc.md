## The problem

A friend testing memoria on macOS reported a screenshot showing concurrent queue corruption. Investigation revealed a race condition in how `pending.yaml` and `status.yaml` are written.

## Root cause

Two or more writers overlap in the load→save window of the queue and status files:
- Parallel agent sessions fire hooks at the same time
- `memoria process --all` (cron timer) runs `queueRemove` while a hook runs `queueAdd`
- Each operation loads the file, modifies it in memory, and writes it back — the window is only milliseconds per write, but hooks fire on every prompt/session-start/end, and cron runs on a timer, making the race condition **certain eventually**

Consequence: a lost `queueAdd` means a digest never gets processed, and the session is silently lost forever. With `--auto-apply` on, nobody notices or re-checks.

## The fix

File locking with exclusive `syscall.Flock` on sidecar `.lock` files — simpler than append-only queue redesign ([[decisions/0007-queue-safety-via-file-locking]]):

- **`flock.go` (new)**: `withFlock(path, fn)` takes exclusive lock on `<path>.lock`, calls the function atomically; `writeFileAtomic` writes to temp file, then renames (atomic on POSIX)
- **`queue.go`**: all four writers (`queueAdd`, `queueEndOthers`, `queueRemove`, `queueMarkEnded`) wrapped in `withFlock`; `saveQueue` uses atomic rename
- **`status.go`**: `statusSet` same treatment (parallel projects also clobbered each other's status entries)
- **Readers** (`loadQueue`, `runStatus`) stay lock-free: atomic rename means they always see a consistent snapshot; a digest added mid-run waits for the next cron pass, nothing lost

Test added: `TestQueueConcurrentAdds` — 20 goroutines add simultaneously, verifies zero lost updates (fails without the lock).
