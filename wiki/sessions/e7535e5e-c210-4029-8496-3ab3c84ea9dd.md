## Part 2: CI/CD pipeline and branch protection

Request: "I want to setup a github to build the CLI and create a release whenever we merge a PR on branch main. We must create a AI rule to always update the version, to keep it consistent, then create the workflow to it. The CLI will have the main branch blocked, we will need to create a new branch and after that a PR to merge on main (try setuping this with GH cli...)."

Recon (Explore agent) found: no existing CI at all (no `.github/`, no goreleaser, no Dockerfile — greenfield); `scripts/build.sh` already had a cross-compile matrix (`build.sh all`: linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, `CGO_ENABLED=0`) that a release workflow could reuse directly; `scripts/install.sh` already carried a `ponytail:` note about swapping its `go install @latest` path for a release-binary download "once github releases exist"; the version const lives solely in `cmd/memoria/main.go:10-11`, read by the `version` subcommand and the MCP handshake; the repo remote is SSH (`git@github.com:johnvilela/memoria.git`), public, default branch `main`, `gh` authenticated with `repo` scope (no `workflow` scope, but SSH push isn't blocked by that); only one tag existed (`v0.7.0`), zero GitHub releases, and the const-vs-tag drift found in Part 1 was already visible in the recon.

Built and shipped on branch `ci/release-pipeline` → **PR #2**:

- **`.github/workflows/ci.yml`** — on every PR to main: a `test` job (`scripts/test.sh`) and a `version-check` job that fails if `*.go`/`go.mod` changed without a bump to `const version`, or if the resulting tag already exists; docs-only PRs pass automatically.
- **`.github/workflows/release.yml`** — on push to main: reruns tests, then if tag `v<version>` is new, cross-compiles via `scripts/build.sh all`, generates sha256 checksums, and publishes a GitHub release via `gh release create --generate-notes`. A no-bump merge skips the release quietly.
- **`AGENTS.md`** — new AI rule: bump the version on every code PR, never tag or release by hand.
- **`wiki/skills/release-ritual.md`** — edited in-session to mark steps 4–6 (the manual commit/tag/push) partially superseded.
- **`scripts/build.sh`** — edited twice in support of the release workflow; Windows was deliberately not added to the build matrix (still linux/darwin × amd64/arm64 only) — `flock.go`, `process.go`, `status.go` use unix-only syscalls (`syscall.Flock`, `Setsid`, `Kill`) that don't compile there, so Windows binaries need a real port with `_windows.go` build-tagged variants first. Tracked with a `ponytail:` comment in `build.sh`.

Branch protection: a **`protect-main`** GitHub ruleset was created via `gh api repos/johnvilela/memoria/rulesets -X POST` (not the web UI) — PRs required (0 required approvals, solo repo), both `test` and `version-check` checks required, no force-push, no branch delete, and no bypass actors at all.

Verified end to end: PR #2's checks passed (`gh pr checks 2 --watch --fail-fast`); merged (squash, branch deleted); the release workflow fired automatically and published **v0.8.0** with 4 platform binaries + checksums (`gh release view`); the downloaded `memoria_linux_amd64` binary printed `memoria 0.8.0`; an empty probe commit pushed directly to `main` was rejected by the ruleset, then reset (`git reset --hard origin/main`) to clean up.

Noted consequence: memoria's own opt-in wiki auto-commit, if enabled, would now have its push to `main` rejected too — wiki updates need a branch + PR under the new protection, or auto-commit can just stay off (already the default).
