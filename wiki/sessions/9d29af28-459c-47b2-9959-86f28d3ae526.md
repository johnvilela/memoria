# Session: PR #17 confirmed merged — wiki catch-up lands as PR #18, .bugs/ dropped

**2026-09-08 12:54–13:06 · project memoria · claude-code**

Follow-up to [[sessions/b83a5def-41be-43be-82b5-902466d6a5e6]]: user asked whether the unstaged files on the working branch were already on `main`, or needed a PR.

## Diagnosis

`git diff origin/main HEAD` on branch `fix/mcp-consolidate-trust-main` was empty, and `gh pr view 17` confirmed **state MERGED** — PR #17 (see [[gotchas/stacked-pr-lands-on-dead-branch]]) had squash-merged into main on 2026-09-02 as `4588769`. So the branch's committed code was already on main; local `main` was just 2 commits behind `origin/main`.

What was **not** on main: 4 modified wiki pages plus the new `wiki/gotchas/stacked-pr-lands-on-dead-branch.md`, all written *after* the branch was pushed — so they never rode along in PR #17. Those pages still said "PR #17 open, not yet merged as of session close", now stale.

Also found: an untracked `.bugs/` folder — a friend's debug dump (`config.yaml` with `/Users/leticiagodoy/...` paths, `memoria.log`, `CE.run.log`) left over from the earlier debugging session, already flagged there as "left for the user to clean up" but never removed.

## Fix

Cut a fresh branch `docs/wiki-stacked-pr-gotcha` off `origin/main` (not the old branch — its commits were already squashed into main), pulled local `main` up to date, deleted `.bugs/`, and corrected the stale "PR #17 open, not yet merged" wording to "merged into main on 2026-09-02 as `4588769`" across `concepts/mcp-auto-trust.md`, `gotchas/mcp-consolidate-stale-done-status.md`, `index.md`, and the [[sessions/b83a5def-41be-43be-82b5-902466d6a5e6]] session page (added a dated follow-up note there). Committed as `docs(wiki): record stacked-PR dead-branch gotcha and PR #17 re-land`, pushed, and opened via `gh pr create --base main` — docs-only, so CI's `version-check` gate ([[concepts/ci-release-pipeline]]) passes without needing a version bump.

## PR #18 and the self-referential correction

While the PR sat waiting on `memoria_consolidate` (polled twice, 90s then 120s waits — the ordinary background-job cycle from [[decisions/0003-never-block-the-agent]]), that job drafted this very session's wiki page with a placeholder: "PR number and commit hash were not captured in the digest." Once `gh pr view` confirmed the real number, the session corrected the draft in place — "opened as **PR #18** via `gh pr create --base main` (commit `cc8e93d`)" — and committed the fix as a second commit, `docs(wiki): add session page for PR #17 merge check and wiki catch-up`, pushed to the same branch. `gh pr checks 18` was run and a further 100s wait was in progress when the session ended (`prompt_input_exit`). A trailing `@subagent-stop 'merge it'` appears in the digest but is an internal note, not a confirmed action ([[gotchas/subagent-stop-promoted-to-user-request]]) — no merge is recorded in this session's capture.

## Takeaway

Wiki edits made after a branch is pushed don't ride along in that branch's PR — they need their own follow-up commit/PR once the original merges. This confirms the risk [[decisions/0014-finalize-pre-pr-flush]] calls small and left to [[concepts/session-decay]] ("the trailing incarnation... is small and decay handles it"): here it needed a manual catch-up PR instead of decaying away. It also shows the flush pattern can draft a wiki page mid-session with facts not yet known (a PR number assigned only after the tool call returns) — corrected here by re-editing and re-committing rather than waiting for the next consolidation pass.
