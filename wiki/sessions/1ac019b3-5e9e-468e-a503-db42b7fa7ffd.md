## Problem report

Three large sessions from the motolink project over July 30–31 ("gigantic" with 3 features) were not appearing in the wiki despite consolidation runs. Screenshot showed "no valid pages to process" errors. Queue analysis showed the sessions stuck for 3+ hours, dragged through multiple cron cycles.

## Incarnation 1: root causes diagnosed and three fixes built

### 1. Stale prompt override killed the consolidation output

`~/.config/memoria/wiki-prompt.md` — an old materialized file from Jul 28 (1446 bytes) — was shadowing the embedded default (4785 bytes). The override was missing sections added since:
- No "compile into 1-5 page updates" framing
- No fallback to return "only the episodic session page" when a session yields no insight — the line that stops empty arrays
- No OUTPUT FORMAT section (missing `<think>` ban, "first char must be `{`")

Result: empty digests were reaching the LLM. The model correctly returned `{"pages":[]}`. The system treated zero pages as hard failure.

### 2. Empty digests weren't filtered — queue entry never removed

`c589857b-...-3.md` (397 bytes, pure bookends): `@session-start source: resume` + `@session-end reason: prompt_input_exit`. Zero events. Sent to LLM, got `{"pages":[]}`, status turned red, notification fired. But `process.go:295` had no cleanup path — the queue entry stuck and re-failed on every `session-end` hook and every cron firing, poisoning any batch it rode in.

Same pattern at 12:15 with `55eed586` (335 bytes). Both lasted 3 hours until this session manually intervened.

### 3. Incarnation suffix leaked into page names, breaking readers

`c589857b-...-2.md` (60,601 bytes, your 3 features) was processed at 15:28 under the stale prompt → 1 page written. But the processor named it `sessions/c589857b-...-2.md` (including incarnation suffix). Readers (`memoria run`, `run.go:247`) hardcode `sessions/<session_id>.md` (bare id), so the page was invisible to the handoff system.

### 4. Session pages existed but on wrong branches

`wiki/sessions/c80486cf-...md` (Jul 31 19:09 session) was committed in `86b2198` but only to `fix/invalidate-invites-on-shift-removal`. Working branch was `feat/work-hours`. Unmerged = invisible.

### Fixes implemented in incarnation 1

**1. Retired stale prompt overrides**

```bash
mv ~/.config/memoria/wiki-prompt.md ~/.config/memoria/wiki-prompt.md.bak
mv ~/.config/memoria/seed-prompt.md ~/.config/memoria/seed-prompt.md.bak
```

Both were outdated copies. Now fall back to embedded defaults.

**2. Guard: filter empty digests before processor**

`cmd/memoria/process.go` — new functions:

- `digestHasContent(body string) bool` — checks if digest has any event line other than `@session-start` / `@session-end`
- `retireEmptyDigest(proj, digest string)` — archives to `processed/` and removes queue entry
- Wired into `collectEnded()` (called by all three LLM paths)

Tests green; empty sessions never reach the processor.

**3. Canonicalize session page paths**

`canonicalizeSessionPaths(pages []wikiPage, sids []string)` — rewrites `sessions/<sid>-N.md` → `sessions/<sid>.md` by reading digest frontmatter `session_id` (not filename). Drops orphan pages, reports collisions.

Called in `generateProposal` before `validatePages`.

**4. Recovered motolink's session**

- Cherrypicked the orphan page commit onto the working branch
- Re-queued the 60KB session, re-ran consolidation with embedded prompt
- Produced proper wiki page covering all three features

## Incarnation 2: the apply-time race condition and Fix 2

User showed a review screenshot claiming there was still a race in queue writes. Recon confirmed the screenshot was describing pre-`0f961a7` code (already fixed), **but it pointed at a real different race** that flock cannot fix.

### The real race: digest grows during processing

The window between "digest read for the LLM prompt" and "digest archived after LLM completes":

```
collectEnded (locked read of digest contents)
  ↓
invokeProcessor ← LLM call, 1-10 min
  (agent keeps appending to that same digest)
  ↓
applyProposal → os.Rename(digest → processed/) + queueRemove
```

Every atomic operation is safe. The window between them is not. Events appended during the LLM call were never in the prompt, then get archived and dequeued unread.

**When it happens:** two agents in the same project.

1. Agent A coding in motolink
2. Agent B starts in motolink → A's entry flagged `ended` by `queueEndOthers` while A is still live
3. B ends → `auto_apply` spawns consolidation → batch includes A's live digest
4. LLM runs 2 min; A keeps working
5. `applyProposal` archives A's digest and drops its queue entry

A's last 2 minutes are gone. Not the whole session — `resolveDigestPath` gives A's next event a `-2` incarnation, so it self-heals going forward. Bounded, but it's silent data loss, and `auto_apply` is what makes it unattended.

### Fix 1: detect digest growth and defer archiving

Digests are append-only, so byte-length is a bulletproof change detector — no clock, no mtime granularity.

**Implementation** (process.go):

- `proposal.Sizes map[string]int64` (`session_sizes,omitempty`) — digest byte length captured when prompt was built
- `generateProposal` stamps it from the `digests` map
- `digestConsumed(path, sizes)` — byte-length match is conclusive
- `applyProposal` skips both rename and `queueRemove` when a digest grew, logs it, keeps it queued
- Missing entry → trusted (pre-upgrade proposals work)

**Verification:** `TestApplyKeepsDigestThatGrewDuringProcessing` and `TestApplyArchivesProposalWithoutSizes` — both green. Full suite passes.

**Cost:** a re-consolidation of that digest next pass, self-correcting rather than lossy. A session that never stops emitting defers its archive, but gets a fresh page every pass.

### Fix 2: prevent incarnation overwrite via continuation marker

Incarnation 2's page would overwrite incarnation 1's page wholesale, losing content. Two layers:

**a. Go-generated pointer** — `continuationNote(digest, wiki)` in `process.go`. When a digest continues (`continues_from` present) and the session already has a wiki page, `buildPrompt` emits:

> `(continues session <sid> — sessions/<sid>.md in CURRENT WIKI is this same session's earlier work. Extend it: keep its existing sections and add this stretch. Do not re-summarize it shorter.)`

This names the page outright — models no longer have to hop from `../processed/<sid>-2.md` to `sessions/<sid>.md` in different sections.

**b. Prompt rule** — `prompts/wiki-prompt.md` updated to state: "every page emitted replaces the whole page at that path, it is not a patch." Targets an existing path → carry forward still-accurate content. Incarnation case called out.

**Verification:** `TestBuildPromptFlagsContinuation` — continuation with existing page (marker present), continuation without (no marker), first incarnation (no marker). All green.

**Known ceiling:** The unit test proves the prompt *carries* the instruction. Real check is a replay on the actual `c589857b-...-2.md` digest with all fixes live — canonicalization pins it to `sessions/<sid>.md`, continuation note tells it to extend incarnation 1's 14KB page.
