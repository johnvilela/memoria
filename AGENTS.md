# memoria

## What

Go CLI that gives code agents long-term memory and a per-project wiki, built from their chat sessions. Knowledge (decisions, rules, strange bugs) is captured from agent conversations, consolidated into markdown files inside the project folder, and read later by humans or by future agent sessions.

Deeply inspired by Fabio Akita's ai-memory and Andrej Karpathy's LLM wiki idea.

## How it works

- **Hooks**: code-agent hooks (e.g. Claude Code hooks) trigger knowledge capture at the right moments.
- **Cronjobs**: periodic consolidation of captured knowledge into curated markdown knowledge files.
- **Markdown in the repo**: no database, no embeddings — plain `.md` files living in the project folder. Per-project memory in the MVP.

Differentiator vs. existing solutions: hooks + cronjobs + markdown files, human-readable and agent-readable, versioned with the project.

## Stack

- Go, entrypoint in `cmd/` (no Go files in repo root); build with `go build -o memoria ./cmd`
- CLI dispatch: stdlib `os.Args` switch — no cobra/urfave
- TUI/styling: charmbracelet/lipgloss + bubbletea/bubbles (interactive selects and inputs live in `tui.go`)
- Module: `github.com/johnvilela/memoria`

## Conventions

- **TDD**: write tests first for every feature, confirm red, then implement to green.
- Docs, help text, and code in English.
- Help screen lists only real commands; planned commands are tagged "coming soon".
- **Version bump on every code PR**: any PR touching `*.go`/`go.mod` must bump `const version` in `cmd/main.go` (CI blocks the merge otherwise; semver per `wiki/skills/release-ritual.md`). Never tag or `gh release create` by hand — merging to main tags `v<version>` and publishes the release automatically.
- Main is protected: no direct pushes — branch, PR, green checks, merge.

## Scripts

- `scripts/build.sh` — host binary at `./memoria`; `scripts/build.sh all` → `dist/` for linux/darwin × amd64/arm64 (windows pending a syscall port)
- `scripts/install.sh` — installs to `$BIN_DIR` (default `~/.local/bin`); in-repo builds local checkout (needs Go), standalone downloads the latest release binary, checksum-verified (curl-able from github)
- `scripts/test.sh` — `go vet` + `go test -race` via gotestsum (testdox: ✓ per scenario), extra args pass through (`scripts/test.sh -run TestX`)
- `scripts/dev.sh` — dev loop: build the local checkout and install to `$BIN_DIR` (wraps `install.sh`)

## How hooks flow

1. `memoria init claude-code` merges command hooks into `~/.claude/settings.json` (Codex: `~/.codex/hooks.json`, same JSON shape; Codex lacks the Notification event and needs one-time `/hooks` trust in its TUI). Idempotent; preserves existing settings/hooks; uses the absolute binary path.
2. Each agent event runs `memoria hook <canonical-name> --client <claude-code|codex>` with a JSON payload on stdin — the client flag is baked in at install time (payloads don't name the agent) and lands as `client:` in digest frontmatter, which `memoria run` uses to pick native resume vs handoff. Re-running init re-points existing hook commands in place (covers moved binaries and pre-`--client` installs) (`session_id`, `cwd`, `hook_event_name`, ...). Canonical names: `session-start user-prompt pre-tool-use post-tool-use pre-compact post-compact notification stop session-end subagent-start subagent-stop`; unknown names are ignored.
3. Hooks are global, but capture only happens for projects opted-in via `~/.config/memoria/config.yaml`. Run `memoria bootstrap` inside a project to register it (idempotent):
   ```yaml
   projects:
     - name: some-project
       path: /home/me/dev/some-project
   processor: claude-code       # set by memoria init; processes sessions into wiki/memories
   gemini_api_key: ...          # only when processor is gemini; config written 0600
   auto_apply: true             # autopilot: session end consolidates, proposals + lint fixes apply without review
   wiki_auto_commit: true       # opt-in: commit the wiki after every applied write (off = commit it yourself with memoria commit)
   wiki_commit_message: ...     # optional pattern for wiki commits (auto and manual); placeholders {action} {summary} {count} {project}
   decay_soft_days: 15          # optional: days a sessions/ page can go unused before the sweep trashes it (0/absent = 15)
   decay_hard_days: 30          # optional: days before an unused trashed sessions/ page is purged for good (0/absent = 30)
   ```
   ```yaml
   global: true                 # bootstrap --global: capture unregistered folders too
   global_path: /abs/path       # optional global root; empty = ~/.config/memoria
   ```
   `cwd` is matched by longest path prefix; untracked projects are silently ignored — unless `global: true`, which routes them to the `_global` pseudo-project (`resolveProject` in config.go): digests land under `<global-root>/.memoria/` (never in the source folder) with frontmatter `project:`/`project_root:` naming the real source folder, queue/status pool under the `_global` key, and `process`/`lint`/`digest` and every `mcp` tool from an unregistered cwd resolve to the global root (empty `session_id` = newest global session). The global wiki is hybrid: shared root categories plus per-source-folder namespaces (`<folder>/concepts/...`, allowed only in global mode by `validPagePath`); a Go-side prompt addendum + a global contract variant teach the split. Commit policy is pinned by `globalCommitCfg`: default root always commits (its wiki is its own repo), `global_path` never does. Bootstrap also appends `.memoria/` to the project's `.gitignore` (captures stay untracked) and creates `wiki/` with a `.gitkeep` (the curated wiki is meant to be versioned). An existing wiki folder is adopted as-is (a non-directory at the wiki path is an error — pick another name with `--wiki <name>`); the name is saved as `wiki:` on the project entry (empty = `wiki`).
4. Captured events append chronologically to the session digest at `<project>/.memoria/sessions/pending/<session_id>.md` as `@hook` annotated lines (see "How digests flow"). Events not worth digesting write nothing: `pre-tool-use`, `notification`, `subagent-start`, unknown hooks, and tools other than Write/Edit/NotebookEdit/Bash. Reopening a session whose digest was already processed starts a new incarnation (`resolveDigestPath` in `hook.go`): `<sid>-2.md`, `<sid>-3.md`, ... in pending/, frontmatter `continues_from: ../processed/<previous>.md`; the processed original is never touched.
5. `<project>/.memoria/sessions.md` indexes sessions as `DATETIME - SESSION_ID - NAME` — the name is the session's first user prompt (whitespace-collapsed, truncated to 80 runes). One entry per session id.
6. Creating a digest also registers its absolute path in `~/.config/memoria/pending.yaml` (`queue.go`) — the central worklist `memoria process` consumes, grouped by project name. An entry becomes `ended: true` when `session-end` fires OR when a new session starts in the same project (`queueEndOthers` — crashed/abandoned sessions don't stay pending forever). Append + dedupe only; `process --apply` removes entries:
   ```yaml
   memoria:
     - path: /home/me/dev/memoria/.memoria/sessions/pending/abc-123.md
       ended: true
   ```
7. `memoria hook` must NEVER block an agent: always exits 0, never writes stdout (some agents inject hook stdout as model context).
8. With `auto_apply: true`, `session-end` also spawns a detached `process --foreground` for the project (`autoConsolidate` in `hook.go`) — best-effort and logf-only, skipped when the project's job slot is busy. Only explicit session ends trigger; sessions ended implicitly by `queueEndOthers` are swept by the next trigger or the cron. The digest command is not spawned: the batch prompt already emits the `sessions/<sid>.md` page.

## How processing flows

1. `memoria process` (inside a tracked project) collects this project's `ended: true` queue entries whose digest file still exists. None → "Nothing to process". With work to do it detaches: re-execs itself as `process --foreground` (setsid, no stdio) and returns immediately, recording `state: running` + pid in `~/.config/memoria/status.yaml` (`status.go`). A second `process` while one is running for the project is refused (pid liveness check — a dead pid is respawned over). The child writes the final `done`/`error` state + detail; `memoria status` prints it, flagging a running entry whose pid died. With `notifications: true` the child also fires a notify-send desktop notification on success ("proposal ready") and failure (`notify.go`; Linux only, errors just logged).
2. Prompt = go:embed default (Karpathy-style wiki maintainer: FAITHFULNESS first, wikilinks incl. `[[project:...]]`/`[[_global:...]]` as plain text, output language follows the input), overridable by creating `~/.config/memoria/wiki-prompt.md` + full current wiki content (trash/ excluded) + session digests + a Go-appended JSON output contract (kept out of the editable file so edits can't break parsing).
3. The configured processor runs it (`processor.go`): `claude-code` → `claude -p --model <processor_model|sonnet>`, `codex` → `codex exec -m <processor_model|gpt-5.4.mini> -c model_reasoning_effort=<processor_effort|high>` (wiki work is text digestion, but it has to escape quote-heavy markdown into JSON strings — haiku drops backslashes there often enough to cost whole batches, so claude defaults to sonnet; overridable via `processor_model`/`processor_effort` in config.yaml; cwd = project dir when it has `.git` — codex trusts git repos; otherwise temp dir + `--skip-git-repo-check`; claude always cwd = temp dir; both get `MEMORIA_NO_CAPTURE=1` as recursion guard, 10-min timeout), `gemini` → `generateContent` REST call, `ollama` → "coming soon" error.
4. The LLM returns a ConsolidatedBatch `{"pages":[{"path","title","tags","body_markdown"}]}` (1-5 pages; the episodic session page goes at `sessions/<sid>.md`) — it NEVER writes files. Every processor reply (process, digest, lint report, lint fix, seed) goes through the one parser in `jsonout.go`: `extractJSON` (tolerates fences/chatter) → unmarshal → on failure a deterministic `repairJSON` pass and one retry. Page bodies ride inside JSON strings, so the model must escape every `"` in them; one dropped backslash used to kill a whole batch. `repairJSON` re-escapes a quote whose next non-space byte is not `,` `:` `}` `]` (in valid JSON that can't happen, so it is the identity function on valid input) and escapes raw control chars — no second LLM call. A repaired run still applies, but says so in the log, in `out`, and in the `memoria status` detail (`— output repaired`). Known ceiling: a stray quote immediately before a comma is indistinguishable from a terminator and still fails. Any parse failure (and every repair) dumps the raw output plus a window around the `json.SyntaxError` offset to `<project>/.memoria/last-processor-error.txt`, one file, overwritten per run. Then Go validates every page (`validPagePath`: path is `index.md`, under a native category (`concepts/ decisions/ gotchas/ rules/ sessions/` — suggestions, not the only options), or under any top-level folder already present in the wiki; `.md` only, no traversal, nothing empty; `trash/`, `_global/` and dot-folders are reserved — the LLM may not invent new top-level folders). Invalid pages are dropped with a printed `warning:` (also logged, dropped count lands in the status detail); the run fails only when zero valid pages remain. The result goes to `.memoria/proposal.json` with project/sessions metadata. The lint fix pass keeps the old `{action,path,title,content}` shape (`lintPage`); its `delete` action moves the page to the wiki's `trash/` (same mechanics as `memoria_delete_page`). `process` and re-run `bootstrap` warn when the wiki contains a reserved `_global/` folder.
5. After human review, `memoria process --apply` re-validates, writes the pages under the wiki folder (`writeWikiPage` = `renderPage`'s `tags:` frontmatter + the deterministic `lastUsed:` stamp on `sessions/` pages, preserving an existing page's date and overriding anything the LLM authored; seed, digest and `memoria_write_page` share it; `lintApply` writes raw LLM files and re-injects `lastUsed` via `stampSessions`), moves the digests to `.memoria/sessions/processed/`, removes their queue entries, and deletes the proposal. Then `commitWiki` (wikigit.go) stages and pathspec-commits the wiki folder — but only with `wiki_auto_commit: true`, which is off by default; otherwise the wiki is left dirty for `memoria commit` or the user's own commit (message from `wiki_commit_message`, default `docs(wiki): {action} — {summary}`; same call at the tail of lintApply/seedWiki/digestForeground; MCP write_page/delete_page never commit — mid-session edits belong to the user's own commit; failures logf-and-skip). MCP agents review + apply the same proposal via `memoria_consolidate`.
6. With `auto_apply: true` the review gate disappears: `generateProposal` applies its own proposal inline (status detail "applied N pages...", `processAll` skips its second apply so `--all --apply` doesn't double-fire), lint's `generateLintReport` runs `lintApply` right after writing findings (failed auto-fix keeps the report for manual review), and the cron timer effectively applies regardless of `cron_apply`. `mcpConsolidate` recognizes the applied-done status so polls report done instead of respawning.

## How the cron flows

1. `memoria init --cron <schedule>` (or `memoria setup --cron ...`) installs an OS-native scheduler (picked by `runtime.GOOS`), then saves config — loader failures are warn-only, the artifact + config are the state.
   - **Linux (systemd):** writes two units to `~/.config/systemd/user/`: `memoria-process.service` (`Type=oneshot`, `ExecStart="<abs memoria>" process --all`, plus ` --apply` when `--cron-apply`) and `memoria-process.timer` (`OnCalendar=...`, `Persistent=true`), then `systemctl --user daemon-reload` + `enable --now`.
   - **macOS (launchd):** writes a LaunchAgent plist to `~/Library/LaunchAgents/com.jv77.memoria.process.plist` (`ProgramArguments` = `<abs memoria> process --all` [+ `--apply`], `StartCalendarInterval` = the schedule), then `launchctl unload` (old copy) + `launchctl load -w`.
   - Any other OS returns a clear error pointing at `memoria process --all`.
2. Schedules accept presets (`hourly`/`daily`/`weekly`), phrases (`every N hours`, `N times a day` — N must divide 24), or 5-field cron. systemd renders them to OnCalendar (`0 */3 * * *` → `*-*-* 0/3:00:00`; dow numbers → `Sun..Sat`); launchd renders them to `StartCalendarInterval` entries (no step syntax, so intervals are expanded, e.g. `8 times a day` → 8 hourly entries). Ranges (`a-b`) and names are unsupported on both. The verbatim input is saved as `cron:` (+ `cron_apply:`) in config.yaml; `--cron off` disables/removes the artifact and clears both fields.
3. Each firing runs `process --all`: a sequential sweep (the status/queue yaml files have no locking) that skips projects with an already-running job, runs the decay sweep on every remaining project (sessions pending or not), then consolidates the ones with ended sessions, continuing past per-project failures (exit 1 at the end if any failed). Without `cron_apply` the sweep leaves proposals for review — with notifications on, notify-send announces each.

## How digests flow

1. Hooks write the digest directly — there is no separate digest command, raw log, or AI pass. The first captured event of a session creates `.memoria/sessions/pending/<sid>.md` with YAML frontmatter (`schema_version: 2`, `kind: session-digest`, `session_id`, `project`, `project_root`, `started_at`); every event then appends one `@hook` line (`renderEvent` in `hook.go`):
   ```
   @session-start source: startup
   @user-prompt 'Can you create something'
   @post-tool-use Write /path/file.go
   @post-tool-use Bash 'go build' error: 'exit status 1: undefined: foo'
   @stop 'Done. Created the file.'
   @session-end reason: exit
   ```
2. Lines are whitespace-collapsed but never truncated. Write → `Write /path`; Edit/NotebookEdit → `Edit /path`; Bash → full command; a `tool_response` with a non-empty `error` (or `is_error`) appends ` error: '...'`. Deleted files surface as Bash `rm` lines; recoveries are visible from event order.
3. `session-end` also inserts/updates `ended_at:` in the frontmatter (`setEndedAt`).
4. Recursion guard: `MEMORIA_NO_CAPTURE=1` makes `memoria hook` skip capture entirely (used by tooling/nested agent sessions).

## Project memory (memoria)

Curated long-term memory from past agent sessions lives in `wiki/`:
decisions made, rules to follow, gotchas hit, concepts explained.
Before non-trivial changes: read `wiki/index.md`, then grep `wiki/`
for keywords. Pages carry YAML `tags:` frontmatter for topic lookup.
Prefer the memoria MCP tools when available: memoria_search,
memoria_recall, memoria_digest, memoria_consolidate, memoria_lint,
memoria_write_page, memoria_delete_page.
To recall what a past session did, call memoria_recall (read-only).
memoria_digest WRITES the session's wiki page — only when the user
asks to save the session.
Session pages (sessions/) decay: unused ones move to trash/ after
~15 days and are purged after ~30 (configurable). Reading a page via
search or recall keeps it alive. The lastUsed frontmatter line is
memoria's — never write or edit it.
